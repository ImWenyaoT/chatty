# Chatty 评估

按《深入理解 AI Agent》第 6 章「Agent 的评估」搭建。**评估的对象是模型与 Harness 的组合体**，
不是单独的模型——所以跑的是完整的 `Recommender.recommend()`，不绕开任何一层校验。

## 用法

```bash
uv run python -m evals --level L1     # 先跑基础任务确认链路通
uv run python -m evals                # 全量
uv run python -m evals --json         # 机器可读指标，便于跨模型对比
uv run python -m evals --repeat 3     # 每条任务跑 3 次，得到 Pass^k（稳定性）
uv run python -m evals --retrieval    # 只评检索质量，不调模型、零成本
uv run python -m evals --ablation     # 消融对比：拿掉工具与 Harness 的对照组
```

注意 `--repeat` 会让耗时和费用成倍增加：18 条任务跑 3 次就是 54 次真实模型调用。

会调用真实模型、产生 API 费用。评估框架自身的正确性由 `tests/test_evals.py` 用脚本化模型保证，
不需要联网。

## 教材五要素的落点

| 教材（6.2 评估环境） | 这里的实现 |
|---|---|
| 数据集 | [`dataset.py`](dataset.py) — 18 条任务，分 L1/L2/L3 三级 |
| 环境状态 | 每条任务一个独立临时 SQLite，跑完即弃，保证可重置 |
| 工具接口 | 直接复用生产代码的五个原子工具，不另造一套 |
| 评分标准 | [`rubric.py`](rubric.py) — 三维度 + 否决项 |
| 执行协议 | 单轮请求-响应 |

## 三个刻意的偏离

严格对齐的是方法论，不是组件清单。以下三处是有意不照搬：

**1. 没有用户模拟器。** τ-bench 要模拟用户是因为客服是多轮对话，需要渐进式透露信息。
Chatty 的接口是一次请求进、一个推荐列表出，意图在请求里一次给全。
硬套用户模拟器只会引入不必要的不确定性，降低可复现性。

**2. 没有「流程合规性」维度。** τ-bench 需要事后分析工具调用序列，因为它评的 Agent 没有运行时守卫。
Chatty 的工具顺序是 Harness 的前置条件（`validate_tool_sequence` 不通过就直接抛错），
所以「成功返回」本身就蕴含「工具调用满足依赖顺序」，单独评一维恒为真、没有区分度。
违规会以 `required_tools_not_used` 错误码出现，已被拒绝路径覆盖。
**这是「守卫」和「评分」的区别：守卫让违规无法发生，评分只记录违规发生了。**

**3. 不算加权平均分。** 三个维度是布尔的、量纲不同，
把「政策合规」和「信息完整」平均成一个 3.7 分没有可操作含义。
报告只给二元通过率 + 分维度失败计数。

## 任务集构成

| 难度 | 数量 | 测什么 | 失败意味着 |
|---|---|---|---|
| L1 | 5 | 画像清晰、候选充足的标准路径 | 基础工具调用或流程有问题 |
| L2 | 7 | 预算/库存/类目挤压下的正确子集 | 约束推理弱，Harness 过滤或提示需加强 |
| L3 | 6 | 售罄、无解预算、禁词诱导、不存在的类目 | 抗干扰弱，容易在压力下编造 |

分层的价值是**诊断**——L1 掉分和 L3 掉分对应完全不同的改进方向。

## 首次全量评估结果（2026-07-27，deepseek-v4-pro，18 条）

```
总体：5/18 通过（28%）
按难度：L1 1/5 · L2 3/7 · L3 1/6
错误码：required_tools_not_used ×11、knowledge_not_retrieved ×1、invalid_recommendation ×1
```

### 根因：这是 Harness 设计缺陷，不是模型能力问题

`required_tools_not_used` 占了失败的 11/13。加上诊断字段打印实际调用序列后，
结论非常清楚——**没有任何一次是漏调工具**，全部是这两种形态：

**形态一：顺序换位**（marketing 和 knowledge 互换，两者之间本来就没有依赖）

```
['get_user_profile', 'search_products', 'check_inventory', 'get_marketing_strategy', 'retrieve_knowledge']
                                                            ↑ 期望的顺序是这两个反过来
```

**形态二：重复调用**（模型对结果不满意，合理地再试一次）

```
L2-few-candidates：   search_products 调了 2 次   ← 候选不足，换条件再搜
L3-budget-impossible：search_products 调了 8 次   ← 预算无解，反复尝试后放弃
L2-num-items-overflow：retrieve_knowledge 调了 3 次
```

问题出在 [agent.py](../src/chatty/agent.py) 的这一行：

```python
if context.used_tools != list(TOOL_NAMES):   # 严格列表相等
```

它要求"恰好五个、顺序完全一致、每个只调一次"。但真实 Agent 的合理行为包括：
搜不到就换条件重搜、知识不够就补充检索、无依赖的步骤顺序可互换。
**这些行为全部被判为违规。**

L3-budget-impossible 那条尤其说明问题：预算被压到全场最低价之下，模型搜了 8 次都找不到合格商品，
最终放弃——这是**完全正确的行为**，本该记为"正确拒绝"，却因为 search 调了多次被判成流程违规。

教材 6.1 开篇就强调，评估体系要能区分"模型能力不足"和"Harness 设计缺陷"。
这次评估给出的答案是后者：**28% 的通过率主要不是模型不行，是校验太死。**

### 修复过程：28% → 96%（Pass^3 89%）

评估一共揪出**五个缺陷，全部是自己代码的问题**，没有一个是模型能力不足。

| 阶段 | 单次通过率 | L1 | 改动 |
|---|---|---|---|
| 初始 | 5/18 (28%) | 1/5 | — |
| 一 | 8/18 (44%) | 2/5 | 工具序列改偏序 + 按教材重写工具描述 |
| 二 | 13/18 (72%) | 5/5 | 修中文分词 + 修依据范围语义 |
| 三 | 15/18 (83%) | 5/5 | 加重复调用检测 + 修正一条用例期望 |
| 四 | 17/18 (94%) | 5/5 | **修证据累加**（放宽重复调用时引入的隐患） |
| 五 | 18/18 (100%) | 5/5 | 修参数保真性 + 修正另一条用例期望 |
| 加 Pass^3 | 52/54 (96%) | 15/15 | 修 JSON 解析鲁棒性；**真实稳定性 Pass^3 = 89%** |

**缺陷一：工具序列校验用了严格列表相等**（见上文根因分析）。
改成只校验真实数据依赖的偏序：五个工具都调过（允许重复），
且 `get_user_profile → search_products → check_inventory` 保持先后；
`get_marketing_strategy` 与 `retrieve_knowledge` 之间不约束顺序，因为它们本来就没有依赖。
`required_tools_not_used` 从 11 次降到 1 次。

**缺陷二：中文检索实际上是失效的。** 检索质量评估（见下节）暴露出
`MATCH "价格"` 检索不到「…价格敏感用户…」。根因是 FTS5 的 `unicode61` 分词器
按 Unicode 类别切词，而汉字全属"字母"类，**一整段无空格中文会被当成单个 token**。
之前之所以看起来能工作，是因为种子数据碰巧在词之间写了空格。
修法是索引和查询两侧都按字切分（`chatty.database.segment_for_index`）。

**缺陷三：依据范围用请求参数代替了实际证据。** 原来是
`knowledge_product_ids = set(product_ids) if hits else set()`——
拿模型检索时传的参数当"有依据的商品范围"。诊断输出直接暴露了问题：

```
recommended: ['P001', 'P002', 'P022']
grounded:    ['P022']          ← 模型只传了这一个
knowledge_hits: ['K004']       ← 命中的是「手机购买决策指南」，覆盖整个手机类目
```

改成由**实际命中的文档**决定：绑定具体商品的文档只为该商品提供依据，
未绑定商品的类目通用文档为该类目下所有商品提供依据。

**缺陷四：放宽重复调用时留下的隐患。** 允许工具重复调用之后，
证据记录还停留在"后一次覆盖前一次"的老语义：

```
search_products(['服装'])  → 召回 SUIT-001、P037
search_products(['运动'])  → 召回 P016
recalled_product_ids = ['P016']    ← 前一次的召回结果被抹掉了
```

跨类目推荐时模型分两次搜索是完全合理的行为，却因此被判成"推荐了没召回过的商品"。
四处证据记录全部从 `=` 改成 `|=` 累加。
**这个缺陷是修缺陷一时引入的**——原来"每个工具只准调一次"的严格校验，
正好掩盖了覆盖语义的问题；放宽约束时必须同步检查所有依赖该约束的隐含假设。

**缺陷五：静默的参数转换。** 检索的 query 被截断到前 8 个词，但模型不知道。
教材 4.2 说"模型感知到的世界与工具操作的世界之间不能有系统性偏差，
确需规范化必须在工具描述中说明"。已在描述里写明"query 只取前 8 个词"。

**另外修正了两条自己写错的评估用例**：`L3-budget-impossible` 允许
`required_tools_not_used`（无解时放弃本就是正确行为，表现为没走完五步）；
`L3-category-not-in-catalog` 改名并改成期望成功——我混淆了
`preferred_categories`（软偏好）和 `search_products(categories=)`（硬过滤），
模型搜不到珠宝就按画像真实兴趣推荐，是合理降级而非幻觉。

### 用 Pass^k 重新测量：100% 其实是 89%（后来提到 94%）

单次跑到 18/18 之后，加上了教材 6.4 的稳定性指标——每条任务重复跑 k 次：

```bash
uv run python -m evals --repeat 3
```

| 指标 | 含义 | 首次测量 | RAG 改进后 |
|---|---|---|---|
| 单次通过率 | 所有运行里成功的比例 | 52/54 = 96% | 53/54 = **98%** |
| **Pass^3** | 3 次**全部**通过的任务比例 | 16/18 = 89% | 17/18 = **94%** |
| Pass@3 | 至少通过**一次**的任务比例 | 18/18 = 100% | 18/18 = 100% |

分块 + 查询改写之后 L1 与 L2 达到 15/15 和 21/21 全通过，
唯一还会波动的是 `L3-preference-not-in-catalog`（请求目录里不存在的类目，
模型反复尝试直到轮次耗尽）——这条本身就是边界场景。

**这组数字就是教材表 6-3 的活教材**：Pass@3 是 100%，看着完美；
但真正该看的 Pass^3 只有 89%——之前那次"18/18 全过"是运气好的一次抽样。
教材原话：回归测试用 Pass@k 会掩盖不稳定性，"Agent 五次只成功一次也显示通过"。

**加上 Pass^k 之后立刻抓到一个新缺陷。** 第一轮 Pass^3 只有 78%，
主导失败是 `invalid_recommendation`（5/10），日志里的原因很直白：

```
Invalid JSON: input_value='对 P012（绿联氮化...时快充。"}]}\n```'
```

模型在 JSON 前面写了一句说明文字。提示词明明写了"只返回一个 JSON 对象"，
但模型并不总是遵守——**而这正是 Harness 该兜住的**。
原来的解析只认两种形态（纯 JSON、或完整的 ```json``` 代码块），
补上"从第一个 `{` 到最后一个 `}`"这条兜底后，Pass^3 从 78% 升到 89%。

剩下 2 条时过时不过的任务（`L2-cross-category-churn`、`L3-out-of-stock-switch`）
属于模型侧的概率性行为，不是 Harness 缺陷。

### 另外两条结论

1. **否决项触发次数为 0。** 三轮运行里，没有任何一次幻觉、禁词、售罄商品逃过校验。
   失败全部是"正确地拒绝了不合格的生成"，而不是"错误地放行"。
   证据链那部分的 Harness 是可靠的，出问题的只有工具序列校验这一条。
2. **单次成功率会骗人。** L1 单独跑时通过 3/5，全量跑时 1/5——同样的五条任务。
   这个观察后来被 Pass^k 证实（见上文）：单次跑到 100% 的那一版，Pass^3 只有 89%。

**这就是建立评估基础的意义**：在此之前"Chatty 能不能用"只有主观判断；
现在有了可重复、可归因的数字，并据此定位并修掉了五处具体的设计缺陷。
更重要的是知道了这个数字的边界——Pass^3 = 89%，而不是看上去的 100%。

## 消融对比：Harness 到底值不值

教材第 1 章用**消融实验**验证组件的必要性——逐一关闭某个组件，观察整体表现如何变化。
Chatty 的全部主张是"模型不能决定业务事实"，要证明这不是空话，
最直接的办法就是把约束拿掉，量化坏输出的比例：

```bash
uv run python -m evals --ablation
```

对照的两组用**同一个模型**（`build_model()` 从 `agent.py` 抽出来正是为了这个，
否则比的就成了两个模型谁强），差别只在有没有工具与 Harness：

| | 实验组：完整 Agent | 对照组：裸模型 |
|---|---|---|
| 工具 | 五个 Function Tool | 无 |
| 证据校验 | 三组子集校验 | 无 |
| finalize 重查 | 有 | 无 |

判定标准全部**客观可查**，不依赖任何主观评分：商品是否真实存在于目录、
是否有货、价格是否在用户区间内、文案是否含禁词。

**结果（16 条期望成功的任务）**：

```
对照组共推荐 52 件商品
  目录中不存在（编造 ID）：42 件
  超出用户价格区间：       5 件
  → 不该出现的商品占比：90%
```

编造的 ID 很能说明问题：`B07GNFY3YR`、`B08H99BPJN` 是**亚马逊 ASIN 格式**
（从训练语料里学来的），`ACC0001`、`CLOTH_045` 是凭空编的编号，
还有直接把商品名当 ID 的 `AirPods Pro (第二代)`。

实验组这四类问题**全部为 0**——不是因为模型不犯错，而是因为编造的 ID 过不了
「推荐 ⊆ 搜索召回」的子集校验，售罄与超预算的商品在 finalize 重查时被过滤，
禁词在响应前被强制替换。**三道关都不依赖模型的自觉。**

> **一个容易误读的地方**：报告里"已售罄 0 件"**不是**对照组的优点。
> 它的商品 ID 几乎全是假的，压根查不到对应库存——这两项是**无从判断**，
> 而不是判断通过了。报告在编造率超过 90% 时会自动打出这条警示。

跑了两次，结果分别是 100% 和 90%（模型偶尔会蒙对几个真实 ID 格式）。
对外引用时取保守的 90%。

## 检索质量（教材 3.2 表 3-3）

端到端评估只能说"这次失败了"，但失败可能来自检索没召回、模型没用好结果、或 Harness 拦下了。
所以检索单独度量，用教材给的核心指标。不需要模型，零成本、完全确定：

```bash
uv run python -m evals --retrieval
```

| 指标 | 最初 | 修中文分词后 | 加分块 + 查询改写后 |
|---|---|---|---|
| recall@5（命中率口径） | 70% | 80% | **100%** |
| MRR | 0.7000 | 0.8000 | **0.7833** |

三轮改动各自解决了不同的问题：

1. **修中文分词**（70%→80%）—— FTS5 的 `unicode61` 把整段无空格中文当成单个 token，
   `MATCH "价格"` 检索不到「…价格敏感用户…」。索引和查询两侧都按字切分后修复。
2. **分块**（教材 3.2「结构感知切分」）—— 语料补了 16 篇 300~400 字的长文档之后，
   整篇索引会让检索命中一大段无关内容。现在按句子边界切成 ~160 字的块、相邻块重叠 40 字，
   命中哪块返回哪块。MRR 在这一步略有下降是正常的：候选从 52 篇变成 85 块，
   排序竞争变激烈了，但返回给模型的内容精准得多。
3. **查询改写**（80%→100%）—— 补上同义词扩展后，
   查「保护视力」能命中写着「护眼」的文档，查「电池耐用」能命中「长续航」。

教材表 3-3 还给了第三个指标 **nDCG，这里没有实现**：它要求为每篇文档人工标注
分级相关性（"高度相关"还是"沾边"），标注成本明显高于前两个，
而 recall@k 加 MRR 已经能回答"该找的找到没有"和"找到得够不够靠前"这两个核心问题。

**口径必须说清楚**（教材脚注特别强调）：这里的 `recall@k` 采用教材口径，
即**命中率**（hit rate / success@k）——前 k 个结果里只要有一篇相关文档就算命中，
统计的是查询的比例。学术上标准的 recall@k 是"召回的相关文档数 ÷ 全部相关文档数"，
一个查询有多篇相关文档时两者并不相等。跨来源比较数字前务必先对齐定义。

标注集 10 条查询分三类，刻意覆盖稀疏检索的强项与弱项：词面直接命中、同义表达、过滤范围。
剩余 2 条未召回的都是同义表达（查"保护视力"命中不了写着"护眼"的文档、
查"电池耐用"命中不了"长续航"）——**这是 BM25 的固有边界，不是 bug**，
教材 3.2 说的稠密检索正是为解决它而存在。当前规模下引入嵌入模型不划算，
所以这条边界是有意保留的，并写进了工具描述里告诉模型。

## 已知局限

- **规模小**。18 条任务只够做冒烟级别的回归，不足以支撑统计显著性判断（教材 6.7）。
  要比较两个模型的优劣，样本量远远不够。Pass^3 的 k 也偏小——
  教材举的例子用的是 k=5，k 越大越能暴露长尾的不稳定。
- **没有 LLM-as-a-Judge**（教材 6.5）。所有判定都是规则化的硬检查，
  好处是完全确定、零成本，代价是评不了「推荐理由写得好不好」这类主观质量。
- **没有跨模型对比**（教材 6.6 评估驱动的模型选型）。框架支持注入不同模型，但还没跑过对照实验。
- **数据是合成的**。43 个商品、36 篇知识都是 demo 数据，
  评估结论只能说明 Harness 行为是否正确，不能外推到真实商品目录上的推荐质量。
