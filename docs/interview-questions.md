## A. 项目深挖：最可能被打断的地方

### A1 ⭐ 你说 Harness 校验了五个 Tool，具体校验的是什么对象？

**结论：** 校验的是 `RecommendationContext` 里 Tool 留下的五份可观察证据，不是模型文本。

锚点：`used_tools`（调用顺序列表）、`profile`、`recalled_product_ids`、`in_stock_product_ids`、`knowledge_product_ids`。
`agent.py` 里是集合包含判断：`recommended_ids <= context.recalled_product_ids`，三次，分别对应 `product_not_recalled` / `inventory_not_checked` / `product_not_grounded`。

**边界：** 证据是 Tool 写的，Tool 是我写的；如果 Tool 自己写错证据，Harness 校验不出来——所以 Tool 的证据写入点也有测试覆盖。

### A2 🔥 `used_tools != list(TOOL_NAMES)` 是严格相等。模型多调一次 Tool 就整单失败，这合理吗？

**结论：** 对这个 Demo 合理，对真实 Agent 不合理，我知道代价在哪。

- 合理的部分：这是**流程契约**而不是效率优化。推荐场景下“少调一步库存”是业务事故，宁可失败也不出结果。
- 不合理的部分：真实 Harness 应该区分**幂等重试**（同一个 Tool 重复调用应允许并去重）和**顺序违规**（先推荐后查库存）。现在两者都撞同一个 `required_tools_not_used`。
- 我会怎么改：把校验从“序列相等”换成“**偏序依赖 + 幂等去重**”——每个 Tool 声明前置依赖，Harness 校验拓扑序，重复调用取最后一次。

**这题的真正考点**是你有没有意识到 Harness 的约束强度是可调参数，而不是越严越好。

### A3 🔥 `knowledge_product_ids = set(product_ids) if hits else set()`——模型把所有召回 ID 塞进 `product_ids`，是不是就绕过了 grounding 校验？

**结论：** 是，这是当前实现的已知弱点，我主动说。

现在的语义是“**这次有命中的检索请求覆盖了哪些商品**”，不是“每个商品都有独立引用”。模型只要把候选全塞进 `product_ids`，只要检索整体非空，就能通过。

**正确做法**是逐商品 citation：`KnowledgeHit` 带 `product_id`，Harness 要求每个推荐商品至少命中一条属于它的知识，否则 `product_not_grounded`。代价是知识库覆盖率不足时失败率上升，需要配套“无知识则降级为不带理由的推荐”而不是硬失败。

**为什么现在没做：** 演示知识只有类目级文档，逐商品 citation 会让绝大多数请求失败——这是数据问题不是设计问题。我不会假装它已经解决。

### A4 ⭐ 为什么 `finalize` 要重新读一次 SQLite？启动时不是已经加载过商品了吗？

**结论：** 启动投影是**排序用的特征**，不是**提交响应时的业务真值**。

这是真实踩过的 bug（故事一）：`Catalog` 用启动缓存的商品对象组装响应，库存在运行期变成 0 仍会返回。修复是 `finalize` 里 `self.repository.list_products()` 重读，再过滤 `stock <= 0`。回归测试直接把 DB 库存改 0 然后断言 `no_available_recommendations`。

**延伸一句（加分）：** 这其实是 harness 的通用模式——**读取用于决策，提交前必须重读用于生效**。跟数据库乐观锁、跟 agent 编辑文件前 re-read 是同一个问题。

### A5 🔥 模型已经从 `search_products` 拿到了合规候选，为什么 `finalize` 还要再查一次画像价格范围？

真实 bug（故事二）：Tool 参数是**模型给的**，模型可以传一个比画像更宽的 `max_price_cents`，于是 1899 元商品合法地进了召回集合，Harness 只校验“是否在召回集合内”就放行了。

**教训一句话：** 证据集合只能证明“来路正当”，不能证明“符合用户约束”。**Tool 入参是模型的输出，不是用户的输入**——这句是这道题的核心。

### A6 ⭐ 讲一个你 Harness 抓到而 Prompt 抓不到的错误。

故事三：五个 Tool 全调了，但顺序是先搜索后画像；以及 active 用户读了 new_user 的营销策略。Runner 正常结束，最终输出格式完全合法。

修复：`used_tools` 记顺序；`get_marketing_strategy` 里直接 `segment != context.profile.segment` 就抛 `marketing_segment_mismatch`。

**为什么值得讲：** 它证明了“模型说自己做完了”和“流程真的完成了”是两件事——这是我理解的 Harness 存在的理由。

### A7 指标为什么会同时记成功和失败？

故事四：成功指标写在 `RecommendationResponse` 构造之前，构造抛异常后 except 分支又记一次失败。修复是把 `record_request(success=True)` 移到 response 构造成功之后。

**追问准备：** “你怎么保证以后不再犯？”——回归测试注入构造异常，断言 `successes == 0 and failures == 1`。更根本的做法是**指标只在唯一出口记录**（单一 finally + 结果状态机），而不是散在各分支里。

### A8 `max_turns=10` 这个数怎么来的？

**结论：** 它是**失控保护**，不是重试预算。正常流程 5 次 Tool + 1 次最终输出，10 给了一倍余量。

🔥 追问“为什么不是 20 / 不做自适应”：因为这个流程是固定五步，轮次上限不承担业务语义；一旦上限成为业务参数（比如允许模型自主重试搜索），就得改成**按 token 预算和工具调用成本计费**，而不是数轮数。

### A9 为什么最终输出走文本 JSON 提取，而不是 SDK 的 structured output？

**结论：** DeepSeek V4 Pro 在 Chat Completions 上拒绝 SDK 下发的 `json_schema` response_format，所以保持文本输出，本地用 `_JSON_CODE_BLOCK` 抽 JSON 再交给 Pydantic 校验。

**这题的加分点**是讲清 harness 的可移植性代价：一旦依赖某个 provider 的结构化输出，就把 harness 绑死在一家模型上。现在的做法是**能力下探到最低公共分母（纯文本），结构由本地 schema 保证**，换模型不用改校验逻辑。

**边界：** 代价是解析层要处理 markdown 代码块、前后缀寒暄这些脏输出，我为此留了候选串顺序尝试。

### A10 `thinking: disabled` 为什么要显式关掉？

因为该模型默认返回 reasoning 段落会干扰纯 JSON 输出，而这个任务的决策复杂度不需要长 reasoning。
🧩 **可展开：** Harness 视角下 reasoning 是**成本项和污染源**，不是免费的质量提升——什么任务该开、开了怎么不让它进最终解析、reasoning 内容要不要计入下一轮上下文，这些都是 harness 决定的，不是模型决定的。

### A11 A/B 分桶为什么用 SHA-256 而不是随机数？

**结论：** 需要**无状态且可复现**的分桶——同一个 `user_id + experiment_id` 任何进程、任何时刻都得到同一组，不需要存分配表。
锚点：`sha256(f"{user_id}:{experiment_id}")` 取前 8 字节取模 2。

🔥 追问“为什么要把 `experiment_id` 拼进去”：否则同一批用户在所有实验里落到相同分组，实验之间产生相关性，多实验并行时结论互相污染。

### A12 你的 A/B 有统计显著性吗？

**结论：** 没有，也不声称有。当前只证明了三件事：分桶稳定、两组排序策略确实不同、指标能采集。

没有的部分：样本量、功效分析、方差估计、多重比较校正、指标持久化（现在是**进程内内存**，重启即清零、多 worker 不共享）。
**这题考的是诚实**——把 Demo 的指标说成业务效果是面试最快的死法。

### A13 🔥 指标存在进程内存里，这不是明显的设计缺陷吗？

**结论：** 是缺陷，但是**被记录过的、有取舍理由的缺陷**，不是遗漏。快照里直接标了 `"persistence": "in_memory"`。

理由：这个 Demo 要证明的是 Agent Loop 与校验链，不是指标基础设施。在出现真实瓶颈之前不预先加组件是我的一致立场。
**要改的话怎么改：** 指标写入本来就在 `ExperimentMetrics` 一个 seam 后面，换成 SQLite 表或 statsd 只改这一个类，接口不变——这就是我说的“shape 对上就能换”。

### A14 `sanitize` 只是字符串替换禁词，太朴素了吧？

**结论：** 是的，它是**最后一道兜底**，不是主要手段。

分层看：主要手段是 `get_marketing_strategy` 把禁词和语气作为 Tool Result 送进上下文（**让模型知道规则**）；兜底是 `sanitize` 无条件替换（**不信任模型遵守规则**）。
🔥 已知不足：变体绕过（谐音、拆字、空格）替换不掉；替换成 `***` 可能让文案读不通。真实系统这层应该是独立的合规服务 + 人审抽样，而不是一个 `str.replace`。

### A15 五个 Tool 的边界是怎么划的？为什么不是三个或八个？

**结论：** 划分标准是“**一次确定性数据获取 + 一份可校验证据**”。每个 Tool 恰好写一类证据到 RunContext。

反例：如果把“搜索 + 库存”合成一个 Tool，就丢掉了“召回过但缺货”这个可区分状态，Harness 无法给出 `inventory_not_checked` 这种精确失败码。如果拆得更细（比如价格过滤单独成 Tool），模型的决策负担上升但没有新增可校验状态，纯亏。

**一句话：** Tool 粒度不是按业务模块划，是**按你想校验的证据划**。

### A16 `search` 是在 Python 内存里过滤商品，为什么不写成 SQL？

**结论：** 演示数据量小，内存过滤更易读，也让排序函数（`score`）可以直接单测。这是明确的取舍不是疏忽。

🔥 承认代价：商品上量后这就是全表扫描 + 全量排序；而且 `self.products` 是启动投影，新上架商品要重启才可见。真实系统这里应该是**带索引的 SQL 召回 + 应用层精排**，`Catalog.search` 这个方法签名不用变。

### A17 你的失败码有十来个，为什么不用一个 `agent_failed` 就好？

**结论：** 失败码是**给 harness 自己用的诊断信号**，不是给用户看的文案。

每个码对应一个可定位环节：`required_tools_not_used`（流程）/ `knowledge_not_retrieved`（检索）/ `product_not_recalled`（越界）/ `invalid_recommendation`（结构）/ `llm_not_configured`（配置）。它们同时进指标和日志，出问题时能直接看是哪一类崩的，而不是看 502 数量。

🧩 **可延伸：** 这就是 harness 的可观测性设计——**失败必须是有类型的**，否则你只能靠读日志正文来运维 Agent。

### A18 debug 轨迹记录了什么？不记录什么？

记录 `llm_input → llm_output → tool_call → tool_result → agent_output → response/failure`。
不记录模型隐藏思维过程——**我看不到的东西不会写进轨迹**。

🔥 追问“那你怎么调试模型为什么选错 Tool”：只能从可观察面推断——看 llm_input 里 Tool 描述和上一轮 Result 的呈现方式，改的是**上下文而不是模型**。这正好是 Harness 工程的日常。

### A19 ScriptedModel 测试到底证明了什么？

证明的是：真实 Agents SDK 的 Runner 在收到确定的 Tool Call 序列时，Tool 执行、`call_id` 回填、上下文推进、Harness 校验、错误映射全部按契约工作，且**失败路径可复现**。

不能证明的是：真实模型有多大概率产生正确序列。那是评测的事，不是单测的事。
⭐ **这个区分本身就是考点**——把“测试通过”说成“Agent 好用”会被当场抓住。

### A20 如果让你把这个项目做成通用 Harness，第一步删什么？

**结论：** 删掉“五步固定流程”这个硬编码，把它变成**声明式的 Tool 依赖图 + 通用证据校验器**。

现在 `TOOL_NAMES` 顺序、三次集合包含判断、错误码都写死在 `Recommender.recommend` 里。通用化之后：Tool 声明自己写哪份证据、依赖哪份证据，Harness 只做拓扑校验和证据包含判断，业务不再出现在 harness 层。

**顺带承认：** 我审计过自己这个项目，结论是能删掉约四成——最该删的不是代码而是**说得比做得多的文档**。愿意主动做减法，是我认为工程品味的一部分。

### A21 这个项目上线过吗？

**结论：** 这是可运行可测试的本地 API Demo，它的数据模型和业务规则来自一个真实的电商原型（商品站 + 发货站），不是纯虚构 mock。但它没有跑过生产流量，所以我不会报 CTR、QPS 或可用性数字。

它证明的：Agent Loop、Tool Calling、SQLite/FTS5、业务校验链、错误映射、确定性回归测试。
它不证明的：模型选品效果、并发能力、真实用户反馈。

### A22 🧩 现在给你一周，你会加什么？

按优先级排，每项都要说清**加它是为了证明什么**：

1. **逐商品 citation**（A3 的弱点）——把 grounding 从“范围级”提到“条目级”。
2. **失败自愈**：Harness 检测到 `product_not_recalled` 时，把失败原因作为结构化反馈回灌一轮，而不是直接 502。这是 harness 从“校验器”变成“控制器”的关键一步。
3. **离线评测集**：50 条固定请求 + 断言式判分（不是 LLM 打分），拿到真实模型的流程成功率基线。
   不加的：向量库、消息队列、微服务拆分——没有对应的、被测量过的瓶颈。

## B. Agent / LLM 机制基础（对照 JD 关键词）

JD 点名了：LLM API、KV Cache、Agent Loop、Tool Use、Reasoning、Planning、Skills、MCP、Memory、Subagent、Multi-Agent。下面每条都要能**先给机制、再给 harness 侧的影响**——只答概念定义等于没答。

### B1 ⭐ Agent Loop 到底是什么？一轮里发生了什么？

拼接上下文 → 模型输出（文本 / tool_call）→ 若是 tool_call 则执行并把结果按 `call_id` 追加回消息历史 → 再次调用模型 → 直到产生终止输出或触发上限。

**Harness 侧的影响（这才是考点）：** 谁决定终止？谁决定 Tool Result 怎么呈现（截断、摘要、原文）？谁决定失败要不要回灌？这三件事在 SDK 里都是可替换的，Chatty 里三件都是我自己定的。

### B2 ⭐ KV Cache 对 harness 设计有什么约束？

**机制：** 自回归推理里前缀的 K/V 可复用，命中的前提是**前缀逐 token 相同**。

**Harness 影响（面试要的就是这段）：**
- **稳定前缀原则**：system prompt、Tool 定义、长期记忆这些不变内容必须放最前面且逐字稳定。往 system 里插时间戳、随机 ID、每轮变化的摘要，等于每轮全量重算。
- **只追加不修改**：历史消息一旦改写（比如中途压缩、删掉中间某轮），压缩点之后的缓存全部失效——所以压缩要么不做，要么一次做在一个**明确的截断点**上并接受这一次的代价。
- **多 Agent 的取舍**：subagent 各自独立前缀，缓存不共享；这是 multi-agent 的隐性成本之一。
- 命中率是**可观测指标**，harness 应该把它打出来（provider 的 usage 里通常有 cached tokens 字段）。

🔥 别只背“KV Cache 是缓存 key value 加速推理”——那是模型侧答案，岗位要的是 harness 侧后果。

### B3 Tool Use：一个好的 Tool 定义长什么样？

- **名字即语义**，描述写清**何时该用、何时不该用**（负例比正例更有效）。
- 参数用 schema 约束到最小自由度：能枚举就别开放字符串，能有默认值就别必填。
- **返回结果是给模型读的**，不是给人读的：结构稳定、体积可控、错误信息可操作（“缺 X 参数，请先调用 Y”优于 “ValueError”）。
- 失败要**可区分**：参数错（模型能自己改）vs 系统错（重试无意义）。

Chatty 锚点：`Annotated[int, Field(ge=1, le=20)]` 把非法 limit 挡在 schema 层；`marketing_segment_mismatch` 是让模型知道自己传错了分群。

### B4 Reasoning 和 Planning 在 harness 里怎么落地？

**Reasoning** 是模型内部的，harness 能做的是：决定开不开、决定要不要把上一轮 reasoning 带进下一轮、决定 reasoning 是否参与最终解析（Chatty 是全关，因为任务简单且要纯 JSON）。

**Planning** 有三种落法，各有代价：
1. **隐式**（模型自己决定下一步）——灵活，不可验证，Chatty 之外的通用 agent 常用。
2. **显式计划产物**（先输出 plan，再逐步执行）——可验证、可展示、可人工干预，代价是多一轮和计划漂移。
3. **硬编码流程**（Chatty 的五步）——完全可验证，零灵活性。
**结论句：** 计划的自由度应该由**错误代价**决定，不是由酷炫程度决定。

### B5 ⭐ MCP 解决什么问题？它和 function tool 的区别是什么？

**结论：** function tool 是**进程内的函数注册**，MCP 是**跨进程、跨供应商的工具协议**——它把“谁提供工具”和“谁编排工具”解耦。

价值：同一个 MCP server 可被不同 Agent 产品复用；工具可以独立部署、独立授权、独立升级；用户可以自由配置执行器而不用改 agent 代码。
代价与难点（能讲到这里才算深入）：工具数量膨胀导致的**上下文占用与选择困难**（需要按需加载 / 检索式暴露工具）、**权限与沙箱**、**版本与 schema 漂移**、**延迟叠加**。

Chatty 的位置：五个 Tool 是进程内的，因为它们本质是本仓库的 SQLite 读取，跨进程没有收益。**该不该上 MCP 取决于工具是否需要被复用和被独立授权**。

### B6 Skills / plugins 与 Tool 的区别？

Tool 提供**能力**，Skill 提供**做法**——通常是一段按需注入的指令/流程/资源包，本身不执行任何东西。
Harness 侧要解决的：何时加载（关键词触发 vs 模型自选）、加载多少（全文 vs 摘要 + 按需展开）、加载到哪（system 前缀会破坏缓存，靠后放更安全）、冲突时谁优先。

### B7 ⭐ Memory：短期、长期、工作记忆分别怎么实现？

- **单轮工作状态** → 结构化上下文对象。Chatty 的 `RecommendationContext` 就是这个：业务状态存在对象里而不是自然语言历史里，**Harness 因此不需要从文本反推状态**。
- **跨轮短期** → 消息历史 + 压缩策略。
- **跨会话长期** → 外部存储 + 检索/注入策略。我的立场是**文件式记忆 + 索引摘要 + 搜索工具**，而不是向量库（见 F1）。

🔥 高频追问“记忆怎么防止越攒越脏”：需要**写入门槛**（什么值得记）、**冲突解决**（新事实覆盖旧事实）、**过期与验证**（记录时间、用之前先验证还成不成立）。只谈存不谈治理是不完整的答案。

### B8 Subagent 的价值到底是什么？

**结论：** 主要价值是**上下文隔离**，其次才是并行。

subagent 把一大堆中间过程（搜索结果、文件内容、试错）关在自己的上下文里，只把结论返回主 agent——主上下文因此不被污染。代价：结论之外的信息全丢了，主 agent 无法追问细节；每个 subagent 独立前缀，KV cache 不共享；调试链路变长。

**什么时候不该用：** 任务需要主 agent 掌握细节、或者子任务之间强耦合需要频繁通信时。

### B9 Multi-Agent 怎么拆才不是花架子？

按**接口**拆而不是按角色拆。有效的拆分标准：
1. 子任务的**输出可验证**（否则你只是把不可靠叠成了更不可靠）。
2. 子任务**上下文可独立**（否则通信成本超过收益）。
3. 失败**可局部重试**（否则一个子 agent 挂掉全盘重来）。

反例：“产品经理 Agent + 工程师 Agent + 测试 Agent 开会”——角色扮演不产生可验证接口，只产生 token 消耗。
🧩 这题很适合把 Chatty 反过来讲：五个 Tool 之所以是 Tool 不是 subagent，正因为它们是确定性查询，不需要自主规划（interview-guide 第 3 题）。

### B10 自进化 Agent 你怎么理解？

拆成三个可落地的层次，越往下越难：
1. **上下文级**：把失败经验写进记忆/skill，下次注入——本质是检索，不改模型。
2. **Harness 级**：根据失败统计自动调整流程（改工具描述、加校验、改重试策略）——需要**评测闭环**才安全。
3. **权重级**：把真实轨迹变成训练数据反哺模型——JD 里“模型与 Harness 共同进化”指的是这一层。

**关键判断：** 前两层没有可靠评测就是**自我强化的胡说**。所以自进化的前提是评测，不是记忆。

### B11 超长程任务（long-horizon）的难点是什么？

三个：**上下文预算**（信息量超过窗口）、**误差累积**（每步 95% 正确，50 步只剩 8%）、**状态漂移**（agent 忘了自己在干什么）。

对应手段：外部化状态（文件 / TODO / 计划文档而不是靠记忆）、**每步可验证**（把长任务切成能被自动判定成败的小步）、检查点与回滚、定期用**结构化摘要**而不是自然语言复述来收敛上下文。

### B12 LLM API 层面，harness 要关心哪些参数？

流式与否（影响可中断性和首字延迟）、temperature（工具决策通常压低）、stop 与 max_tokens（截断是最常见的“模型变笨”假象）、tool_choice（能否强制/禁用工具）、缓存字段（读 usage 里的 cached tokens）、超时与重试（**重试必须幂等**，工具已执行过的重试会造成重复副作用）。

## C. Harness 工程：按你的 8 点清单组织

被问“你怎么理解 harness”时，用这套清单答——它比任何背诵的定义都更像内行。开场一句：**模型是厂商的，真正能 DIY 的是 harness；shape 对得上，中间组件可以随便换。**

| # | 清单项 | Chatty 里对应什么 | 我能讲的取舍 |
|---|---|---|---|
| 1.1 | task scheduling / multi-agent | 无（单 Agent，五步固定流程） | 为什么**不**上 multi-agent：无可验证的子接口（B9） |
| 1.2 | loop 与流程控制、可观测性 | `Runner.run` + `max_turns=10` + `AgentDebugHooks` 轨迹 | 轨迹记什么、不记什么（A18）；失败必须有类型（A17） |
| 1.3 | input 拼接：memory / skills / 压缩 | instructions 四段式 + Tool Result 回填 | 稳定前缀与 KV cache（B2）；Chatty 短流程无需压缩 |
| 1.4 | output parser | 文本 → JSON 提取 → Pydantic → Harness 语义校验 | 三层的分工（C1）；不依赖 provider structured output（A9） |
| 1.5 | executor（可配置 MCP） | 进程内 function tool | 什么时候该换 MCP（B5） |
| 2.1 | terminal 执行 / sandbox / 后台任务 | 无（Chatty 不执行代码） | 能讲设计不吹经验：副作用工具需要幂等 + 审计 + 超时 |
| 2.2 | terminal 读 output | 无 | 长输出的截断与摘要策略是 harness 的活 |
| 2.3 | file I/O | 无（数据在 SQLite） | 读改写的 re-read 模式跟 A4 是同一个道理 |

⭐ **诚实原则：** 2.x 三项 Chatty 没覆盖，我会明说“这部分我是作为 Agent 产品的重度用户观察到的，不是我实现过的”，然后讲我观察到的具体设计（比如为什么编辑文件前必须重读、为什么后台任务需要显式的任务表而不是靠模型记住）。**把用户视角讲透，比假装实现过安全得多，也更贴 JD 里“对模型行为有品味、对 DX 有强感知”。**

### C1 ⭐ 你的 output parser 有几层？为什么要分层？

三层，各自解决不同失败：
1. **提取层**（`_JSON_CODE_BLOCK` + 候选串顺序尝试）：处理脏输出——代码块包裹、前后寒暄。
2. **结构层**（Pydantic）：类型、长度、范围、禁止未知字段。
3. **语义层**（Harness）：Tool 顺序、证据集合、业务真值回填。

**为什么不能合并：** 结构合法不代表语义合法（模型可以返回格式完美但根本没查过库存的商品）。这也是 interview-guide 第 8 题的核心。

### C2 🧩 如果让你评价一个 Agent 产品的 harness 好不好，你看什么？

按清单挑三条最能体现差距的说：
1. **失败是否可归因**——出错时你知道是模型选错了、工具挂了、还是上下文超了吗？
2. **上下文是否可控**——用户能看到并干预送进模型的东西吗？（透明度直接决定可调试性）
3. **状态是否外部化**——中断后能否续上？崩溃后能否恢复？

然后举一个你实际用过的产品做正反例。**这题一定要有具体产品和具体细节**，泛泛而谈会被判定为“没重度用过”。

## D. Context Engineering 与上下文管理

### D1 ⭐ 上下文压缩怎么做才不丢关键信息？

**结论：** 压缩的对象不该是“对话”，而应该是“**已经外部化过的中间过程**”。

分层策略：
- **不压缩的**：system、Tool 定义、任务目标、用户显式约束（这些是稳定前缀，压了还伤缓存）。
- **可摘要的**：过去的 Tool Result 长文本——保留结论和引用路径，正文可丢，因为**能被重新获取的东西不需要留在上下文里**。
- **必须外部化的**：决策、待办、已确认的事实——写进文件/记忆，而不是靠摘要在上下文里苟活。

**验证方式**：压缩前后跑同一批任务看成功率差，而不是靠肉眼觉得“摘要写得挺好”。

### D2 上下文里塞太多工具怎么办？

按需暴露：分组 / 按阶段解锁 / 用一个检索工具去发现工具。代价是多一跳延迟，收益是选择准确率和 token 双降。
**判据**：先测“工具数量 vs 选择正确率”的曲线，再决定要不要做——不测就上是过度工程。

### D3 你怎么判断上下文出问题了，而不是模型不行？

可操作的判别法：
- 同一个任务把上下文**手工精简**后重试——好了就是上下文问题。
- 看 llm_input 的**实际渲染结果**而不是你以为拼进去的内容（Chatty 的 debug 轨迹就是为这个存在的）。
- 检查是否触发了 max_tokens 截断（截断的表现极像“模型突然变笨”）。
- 换一个模型跑同样上下文——都错大概率是上下文，只有一个错才是模型能力差异。

## E. 评测、基准与数据（JD 明确职责，务必准备）

### E1 ⭐ 给 Chatty 设计一套评测，你怎么做？

分三层，成本从低到高：
1. **契约层（确定性断言）**：Tool 顺序正确率、证据校验通过率、失败码分布、越价/缺货商品出现率——**全部可自动判定，不需要模型打分**。这是我会先做的。
2. **质量层（有参考答案）**：固定请求集，人工标注“可接受商品集合”，算命中率；理由是否引用了检索到的知识（字符串/实体级可判定）。
3. **主观层（LLM-as-judge）**：文案质量、语气匹配度——只在前两层稳定后才做，且必须报**分数分布而不是均分**。

关键设计：**每层都要能单独归因**。整体成功率下降时，你要知道是模型不调工具了，还是知识库覆盖不够。

### E2 🔥 你用过 LLM-as-judge 吗？踩过什么坑？

**结论：** 用过，最大的坑是**评分锚定**。

我在自己的评估流程里遇到过：评估器把绝大多数样本都判在 8 分附近，均分天花板卡在 8.4 左右，导致**改进前后的差异被压缩到噪声里**——分数看着高、看着稳，实际上没有区分度。

成因：模型对“分数”这个概念有强先验（8 分 ≈ “挺好”），加上 rubric 描述模糊、缺少负例锚点。
应对：**改判据不改分数**——用二元/三元的可判定问题（“是否引用了知识？是否出现禁词？”）替代 1-10 打分；给出带具体样例的锚点；报分布和相对排序而不是绝对均分；同一批样本换评估器交叉验证。

**这个故事很值钱**——它证明你真的跑过评测，而不是只知道概念。

### E3 怎么构建评测基准数据？标注策略怎么定？

- **来源优先级**：真实任务轨迹 > 从真实分布采样的合成 > 纯手工构造。JD 里明说“以真实世界任务作为反馈源”。
- **难度分层**：不能全是简单样例，否则天花板效应（跟 E2 是同一个病）。要留一档明确的“应该失败”的样例——**测 harness 会不会在该失败时失败**，这类样例最容易被忽略。
- **标注策略**：先写判据文档再标注；双人标注 + 一致性检验（分歧率高说明判据不清而不是标注员不行）；把分歧样本单独留档，它们往往指出了任务定义的真实模糊处。
- **防泄漏**：基准要有 held-out 部分，不能被拿去调 prompt，否则你只是在过拟合评测集。

### E4 一个 Harness 改动上线前，你要看哪些指标？

任务成功率（分难度看）、失败码分布（有没有新出现的失败类型）、平均轮数与 token 成本、延迟分位（p50/p95，不看均值）、缓存命中率。
**外加一条：回归清单**——之前修过的每个 bug 都必须有对应断言，否则改 harness 就是在打地鼠。

### E5 🧩 如何评价“这个 harness 改动让 Agent 变聪明了”？

**结论：** 这句话本身不可评测，必须先翻译成可判定的命题。

翻译示例：“在 X 类任务上，成功率从 a 提升到 b，且 token 成本不超过原来的 c 倍”。然后问三件事：样本量够不够？改动前后是否只有这一个变量？失败样例是不是换了一批（有可能是**修好了一类、弄坏了另一类**，均值持平）。

## F. 观点与品味题（拉开差距的地方）

### F1 🔥 你 Chatty 里用了 FTS5 做 RAG，但我听说你反对 RAG，怎么回事？

**结论：** 我反对的是**默认把向量检索当成记忆方案**，不是反对检索本身。

我的判断标准是：**检索结果能不能被验证、能不能被解释**。
- Chatty 用 FTS5/BM25：因为知识是结构化的商品/营销文档，关键词检索**确定性、可复现、可解释**，还能直接进 Harness 的证据链——换成 embedding，我就无法断言“这条知识为什么被召回”。
- 在通用 Agent 场景我倾向**agentic search**（模型自己用 grep/索引摘要/文件读取去找），而不是预先切块灌向量库。理由：切块破坏结构、相似度不等于相关性、索引会过期而文件系统永远是最新的、而且模型能**多轮迭代查询**，一次性 top-k 不能。
- 我也不用 LangChain 这类框架：harness 是我要 DIY 的核心，不该被框架的抽象绑架。

**收尾一句：** 选检索方式的依据是数据形态和可验证性，不是流行度。

### F2 ⭐ 你怎么看“Prompt 能解决就不用写代码”？

**结论：** Prompt 提高正确概率，代码提供保证。**要不要写代码，取决于这件事错了的代价。**

Chatty 的实证：instructions 已经明确写了五步顺序，实际调试中仍出现顺序错误和分群错配，而且 Runner 正常返回、输出格式完全合法（故事三）。如果只靠 prompt，这类错误静默通过。
反过来也成立：文案语气、理由措辞这些**错了代价低、且难以形式化**的部分，我就不写代码校验，交给 prompt 和策略 Tool。

### F3 🧩 你怎么判断一个 Agent 产品的开发者体验好不好？

三个我会立刻去试的动作：
1. **中断它**——能不能干净地停下、停下后状态还在不在。
2. **让它出错**——错误信息是给我看的还是给它自己看的；我能不能从错误定位到具体环节。
3. **改它的上下文**——我能不能看见并编辑送进模型的东西（prompt、工具集、记忆）。

好的 DX 的共同点是**透明可干预**；差的共同点是把 agent 当黑盒魔法卖。

### F4 你对模型行为的“品味”体现在哪？

给具体判断而不是形容词：
- **该失败就失败**优于生成一个看起来合理的兜底（Chatty 宁可返回 502 也不返回默认推荐）。
- **少说多做**：agent 输出应该是可验证的产物，不是过程描述。
- **不要过度确认**，也不要在不该自作主张的地方自作主张——分界线是**动作是否可逆**。
- 一致性 > 偶尔的惊艳：harness 是产品，稳定性才是体验。

### F5 🧩 你觉得 harness 未来最难的问题是什么？

可选一个讲深，别铺开：
- **可验证性**：agent 能力越强，人工验证越贵。长远看必须让 agent 产出**自带验证方式**的结果（测试、断言、可复现脚本）。
- **上下文的经济学**：信息价值 / token 成本这个比值，目前几乎全靠人拍脑袋，缺乏理论和工具。
- **模型与 harness 的边界迁移**：今天写在 harness 里的补丁，明天可能被模型能力内化——所以 harness 的组件必须**可拆卸**，否则会拖着过时的设计跑。这也是我坚持 seam 对齐的原因。

### F6 你怎么用 AI 工具做开发？

要具体到工作流：什么任务交给 agent、什么任务自己写、怎么给它上下文（项目里的 AGENTS.md / CONTEXT.md 就是干这个的）、怎么审查它的输出、什么情况下你会推翻重来。
🔥 **反面加分点**：讲一个你**不**让 AI 做的事和原因，比一味吹效率更可信。比如：我不让它决定架构边界，因为错的边界的修复成本远高于它节省的时间。

## G. 压力题 / 反驳题（准备好被怼）

### G1 “这不就是个加了几个 if 的 CRUD 吗？”

**不要辩解，先承认再区分。** 单看代码确实是查询 + 校验；有价值的部分不在代码复杂度，而在**边界划分**：哪些决策交给不可靠的模型、哪些必须由确定性代码保证、以及**怎么用可观察证据证明模型确实完成了流程**。四个 bug 全部出在这条边界上，没有一个是 CRUD 写错了。

### G2 “Agent 部分是 SDK 做的，你到底写了什么？”

SDK 提供 Loop 和协议；我写的是**完成条件**。SDK 不知道“推荐必须先查库存”，不知道“模型输出的商品必须来自召回集合”，也不知道失败该映射成哪个码。Runner 返回成功 ≠ 业务完成——这个差值就是我的工作量。

### G3 “五步硬编码流程，模型的价值在哪？还不如写个函数。”

**结论：** 在这个 Demo 里模型的价值确实被压得很小——它只负责搜索参数的选择和语义生成。这是**刻意**的：我先证明约束链能立住，再谈放开自由度。

诚实的后半句：如果需求只有这一条固定流程，那确实不该用 Agent。Agent 的价值在于**请求形态多变、流程需要按情况分支**时——那时候硬编码的是五个 Tool 的可用性，而不是它们的顺序。这也是 A20 说的通用化方向。

### G4 “你没有真实流量，凭什么说自己懂 Agent 工程？”

我不声称懂生产运维。我能证明的是：能从可观察面定位 Tool Calling 的失败环节、能把偶发问题固化成回归测试、能识别出 prompt 保证不了的东西。这些能力和流量规模无关，和**是否认真调试过**有关——我有四个具体的 bug 故事，每个都有症状、根因、修复和验证。

### G5 “你的项目是 AI 写的吗？”

**结论：** 大量代码是 AI 辅助写的，这正是我认为该有的工作方式（JD 也这么要求）。区分在于：**设计决策、边界划分、失败模式判断是我的**。

## H. 现场编码 / 系统设计题

### H1 手写一个最小 Agent Loop（不用 SDK）

要点：消息列表 → 调 API（带 tools schema）→ 若返回 tool_calls 则逐个执行并 append `role=tool` 且 `tool_call_id` 对应 → 循环 → 终止条件（无 tool_call / 轮数 / token 预算）。
🔥 面试官爱挖的三个坑：**多个 tool_call 并行返回怎么处理**（必须全部回填后再进下一轮）、**工具抛异常要不要告诉模型**（要，且要写成可操作的信息）、**历史无限增长**（需要预算和截断策略）。

### H2 设计一个工具调用的重试策略

按错误分类：schema 错（把校验信息回灌给模型，让它自己改，可重试）/ 瞬时系统错（指数退避，harness 自己重试，不惊动模型）/ 永久错（直接失败，别浪费轮次）。
**必须提到幂等**：有副作用的工具重试前要有幂等键，否则重试 = 重复下单。

### H3 设计一个 agent 的长期记忆系统

我的取向：**文件式 + 索引 + 搜索工具**。
写入：明确的写入判据（只记不可从代码/历史推导出来的事实）、一条记忆一个文件、带元信息。
读取：加载一个小索引（一行摘要）到上下文，需要时用工具读全文——**索引进上下文，正文进工具**。
治理：冲突时新覆盖旧、记录时间、用之前验证是否还成立（记忆会过期，这是最常被忽略的一点）。
**为什么不是向量库**：见 F1。

### H4 给一个已有 Agent 加可观测性，你先加什么？

先加**结构化的 span**：每轮的 llm_input/llm_output/tool_call/tool_result/最终状态，带耗时、token、失败码。
然后是**可回放**：能用同样的输入重跑一次。
最后才是聚合看板。
**顺序理由**：没有可回放的日志，看板只能告诉你“有问题”，不能告诉你“哪儿的问题”。

### H5 SQLite 换成 Postgres，你要改哪些地方？

只改 `Database` / `CommerceRepository` / `KnowledgeRetriever` 三处；`Catalog` 以上不用动，因为 seam 就划在这里。FTS5 要换成 tsvector 或外部检索，这是唯一有语义差异的部分（排序算法从 BM25 变成 ts_rank，需要重新校准）。
🧩 这题是展示“shape 对上就能换”的最佳机会。

## I. 行为面与项目管理（JD 里这块占了很大篇幅，别裸考）

### I1 讲一个你从 0 到 1 推动的东西

按 **问题 → 判断 → 最小可运行原型 → 迭代依据 → 结果与边界** 讲。重点在“**迭代依据**”——你根据什么决定下一步做什么，这是研究能力的体现。

### I2 你怎么跟不熟悉的技术栈打交道？

给方法而不是态度：先读一手文档和源码而不是二手教程 → 写最小可运行样例验证理解 → 用 AI 辅助覆盖不熟的语法 → **关键结论必须自己验证过再写进代码**。举一个具体例子（比如为了确认 SDK 的 tool result 回填机制，直接写脚本模型跑真实 Runner 观察消息序列）。

### I3 你怎么和研究员协作？

我的定位是**把研究想法变成可跑的实验，并把实验里的工程事实反馈回去**。具体动作：把模糊需求翻译成可判定的评测指标；快速给出原型让讨论有对象；主动报告负面结果（**跑不通、指标没变化，也是结论**）。

### I4 你怎么管跟踪需求、Bug 和排期这类杂事？

JD 里这部分很实在，别表现得不屑。答法：**单一事实来源**（一个列表，不散在聊天记录里）、状态可流转且有人认领、有明确的“下一步和负责人”、延期风险要提前同步而不是到期再说。
可以顺带提：我把项目的约定写进仓库里的 `AGENTS.md` / `CONTEXT.md`，让协作规则跟代码一起版本化——这也是对 agent 协作者友好的做法。

### I5 讲一次你被说服 / 改变主意的经历

考的是**是否用证据改主意**。好的答法：起初我认为 X，直到看到 Y 数据/失败，我改成了 Z。避免“同事说了我就听了”这类没有判据的版本。

### I6 你为什么想做 harness 而不是模型训练？

**结论：** 因为我认为**模型是厂商的，harness 才是能力落地的地方**——同一个模型，harness 不同，可用性天差地别。我的兴趣和积累都在“怎么把不可靠的强能力，变成可交付的稳定产品”这一层。

再补一句真实的使用者视角：我自己是 agent 产品的重度用户，每天都在感受哪些设计让我信任它、哪些让我不敢放手。**这种痛感是做 harness 最直接的燃料。**

## K. 面试前 10 分钟速览

**必须能脱口而出的：**
- 五个证据集合的名字，和它们各自挡住什么错误
- 四个 bug 的一句话版本：旧库存 / 越价 / 顺序与分群 / 指标双计数
- KV cache 对 harness 的三条约束（稳定前缀、只追加、multi-agent 不共享）
- 评测三层：契约层断言 → 有参考答案 → LLM judge（且知道 judge 的锚定坑）
- 8 点 harness 清单

**最容易翻车的五个地方：**
1. 把确定性测试说成模型效果验证（A19）
2. 把 Demo 指标说成业务效果（A12）
3. grounding 校验的弱点被追问时才承认（A3——**主动说**）
4. KV cache 只答模型侧定义、不答 harness 后果（B2）
5. 被质疑“CRUD / SDK 做的 / AI 写的”时急着辩解（G1-G5——**先承认再区分**）

**一句话总纲：** Model 负责不确定的语义，Harness 负责确定的边界；我能讲清这条边界上每一个失败是怎么被发现、被验证、被固化成测试的。
